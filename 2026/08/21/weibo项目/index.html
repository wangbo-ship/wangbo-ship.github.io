（一）架构图

描述

用户自然语言任务输入 到 Agent交互层

Agent交互层包括了 任务理解、参数抽取、缺失参数追问、规划确认、思考过程摘要展示、会话状态/短期记忆

其中的 规划确认 当confirmed=false的时候指向“返回执行计划/缺失参数/待确认”，当confirmed=true的时候指向“Skill调度层”

其中的 会话状态/短期记忆 包括已抽取参数、缺失参数列表、是否确认执行、上下文任务状态

这里当confirmed=true的时候指向的Skill调度层 有如下三条路径到GeoServer服务层

第一条经过sos_to_wfs_skill到”生成SOS请求SML”到query_sos工具 到 SOS服务查询 到 publish_wfs工具 到GeoServer发布WFS图层 到 GeoServer服务层

第二条经过weibo_evernt_analysis_skill 到 微博爬虫 到 kafka缓存 到 java消费 到 Accumulo存储 到 GeoMesa查询/聚合 到 结果服务化输出 到GeoServer服务层

第三条经过wfs_spatial_analysis_skill到 GeoServer MCP/图层发现 到 读取WFS图层 到 空间分析工具层(空间分析工具层包括了 开源GIS分析工具、已有GeoServer内部算法、GeoServer WPS，其中开源GIS分析工具可以指向GeoPandas/Shapely、PostGIS/GDAL、分析结果，已有GeoServer内部算法 和 GeoServer WPS 可分别指向分析结果)，分析结果 到 GeoServer服务层

GeoServer服务层 继续往下可以到 可视化与结果回显：包括了地图展示、服务地址返回、专题结果输出、最终返回用户

Skill调度层 除了以上三条路径到GeoServer服务层之外 还可以直接 执行日志与数据溯源：包括了最终返回用户、stepLogs、输入参数快照、调用的Skill/Tool、中间结果与结果图层、时间戳/执行状态

解析

一、这个项目整体在干什么？

可以把它理解成一条「用自然语言驱动地理数据任务」的流水线：

用户用中文说需求（比如「查武汉市 3 月到 5 月的情感得分，并发布成地图图层」）
→ 系统听懂、补全参数、让你确认
→ 确认后按任务类型走不同 Skill（技能流程）
→ 查数据 / 爬数据 / 做空间分析
→ 最终发布到 GeoServer（地图服务），把 WFS 地址、分析结果 等返回给你

底层涉及：传感器观测标准 SOS、微博时空数据、Kafka 消息队列、Accumulo + GeoMesa 时空库、GeoServer 地图发布 等。

二、先解释架构图里的生僻词

名词 通俗解释
Agent 交互层 和用户「对话」的那一层：听懂你说什么、缺什么参数、要不要执行
Skill（技能） 一条固定业务流程，比如「SOS 查完再发 WFS」
Tool（工具） Skill 里调用的具体动作，比如 query_sos、publish_wfs
SOS Sensor Observation Service，OGC 标准的「传感器观测服务、专用查询接口」，约定用 XML 查观测数据
SML / SOAP SOS 请求常用 XML 格式；你图里的「生成 SOS 请求 SML」在代码里体现为 SOAP Envelope XML
WFS Web Feature Service，通过 URL 提供「矢量图层」给地图软件读取
GeoServer 开源地图服务器，负责发布 WFS/WMS 等图层
Kafka 消息队列，爬虫和 Java 之间异步传数据
Accumulo 分布式数据库；GeoMesa 在它上面做时空索引，适合存带位置、时间的数据
GeoPandas / Shapely / PostGIS / GDAL Python/数据库侧的 GIS 分析工具（架构里有，本仓库暂未实现）
GeoServer WPS GeoServer 的 Web Processing Service，在服务端做空间分析（架构里有，本仓库暂未实现）
MCP Model Context Protocol，让 AI 发现/调用外部工具；图里的「GeoServer MCP/图层发现」是规划能力，代码里还没有

编排中枢：AgentInteractionService.java — 把上面几步串起来。

confirmed=false vs confirmed=true

逻辑在 AgentInteractionService.chat()：

  • confirmed=false（或未确认）
    • 参数不全 → status=COLLECTING_PARAMS，返回「还缺 city、beginDate…」
    • 参数齐全 → status=PLANNED，needConfirmation=true，返回步骤列表问「是否确认执行？」
  • confirmed=true（或说「确认」「执行」）且参数齐全
    • 进入 executeConfirmedTask()
    • 通过 TaskExecutorRegistry 路由到对应 Skill 执行器

对应请求字段：AgentInteractionRequest 里的 confirmed、cancel、userMessage。

会话状态/短期记忆里存什么？

TaskContext 里就是架构图说的那些：

  • slots：已抽取参数（城市、日期、观测属性等）
  • missingInputs：缺失参数列表
  • confirmed：是否确认执行
  • status：任务状态（收参中 / 已规划 / 执行中 / 完成 / 失败 / 取消）
  • 另外还有 plan、stepLogs、artifacts（中间结果如 WFS URL）

注意：当前是内存会话（InMemoryTaskContextStore），重启会丢；文档里写了后续可换 Redis 等。

七、GeoServer 服务层

GeoServer 本身是独立部署的服务（配置在 application.yml 的 geoserver: 段，默认 http://localhost:8082/geoserver）。

本 Java 项目通过 PublishServiceImpl 调用 GeoServer REST API 上传 Shapefile、创建工作区/数据存储/图层，不是把 GeoServer 嵌在 Java 里。

架构图里的「GeoServer 服务层」= 外部 GeoServer + 本项目的发布客户端代码（主要在 sos/service/Imp/PublishServiceImpl.java）。

“动态 Skill 的 tools 只能从「已注册 Tool 列表」中选择；若需要新能力，在 steps 中说明并选最接近的已有 tools”

边界（别误解成「自动写代码」）

已具备 还没有
LLM 规划/定义新 Skill（结构 JSON） 不会自动生成 Java 源码或新 Tool 实现
会话内挂到 context 并走确认执行 Skill 不会持久化成仓库里的新模块
按已注册 Tool 链式调用 Tool 只能从 AgentToolRegistry 已有列表选；多数占位，可能执行失败

所以：「对话生成 Skill 定义并尝试执行」有；「模型从零造出新底层 Tool 代码」没有。

1、前期了解：

WPS 是什么？

WPS = Web Processing Service，不是另装一个独立软件，它是 GeoServer 的一个插件/扩展包。

和 GeoServer 的关系

可以这么理解：

干什么
GeoServer 地图服务器：发布图层、给人看图、查要素（WMS/WFS）
WPS 插件 给 GeoServer 加“计算能力”：缓冲、裁剪、相交、质心等

没有 WPS：GeoServer 主要是“存图层、出图、查数据”。
有了 WPS：才能在服务器上对图层做空间分析。这个 skill 里的「做 500 米缓冲」走的就是 WPS。

PostGIS 是什么？

PostgreSQL 是数据库；PostGIS 是它上面的空间扩展。

装上之后，数据库才能：

  • 存点/线/面几何
  • 用 ST_Buffer、ST_MakePoint 等做缓冲、建点等空间计算

你的项目库是 geodt_db，表如 w_poi（有 lng/lat）。
GeoServer 通过 PostGIS 数据存储 连这个库，才能把表发成图层、并把缓冲结果写回去。

没有 PostGIS：数据库只管普通表；缓冲「算完再发布」这条路在 GeoServer 这边就接不住。
